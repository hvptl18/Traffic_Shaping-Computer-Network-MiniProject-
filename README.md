## 1. Project Overview

This project implements and compares two traffic-shaping and traffic-control algorithms: **Token Bucket** and **Leaky Bucket**.

Network traffic may arrive at different rates. During a burst, packets can arrive faster than the network can process or transmit them. This can cause congestion, increased queue sizes, and packet drops.

The Token Bucket and Leaky Bucket algorithms handle incoming traffic differently. This project uses a Python-based simulation to compare their behavior under baseline traffic and burst traffic conditions.

The simulation records packet transmission, packet drops, queue behavior, and performance metrics. It also generates CSV files and graphs to visualize and analyze the results.

## 7. Working Principles

### 7.1 Token Bucket Algorithm

The Token Bucket algorithm maintains a bucket containing tokens. Tokens are added at a configured rate, up to a maximum capacity.

When traffic needs to be transmitted, the algorithm uses available tokens according to its implementation. The availability of accumulated tokens allows traffic to be transmitted in bursts.

**Advantages:**

* Supports controlled bursts of traffic.
* Can use previously accumulated tokens during periods of high demand.
* Provides flexibility in managing variable traffic rates.

**Limitations:**

* Burst size depends on the available tokens and bucket capacity.
* Incorrect parameter settings may result in excessive drops or insufficient burst handling.

### 7.2 Leaky Bucket Algorithm

The Leaky Bucket algorithm processes queued traffic at a configured rate. Incoming traffic is placed into a queue, and traffic is processed at the rate defined by the algorithm.

If incoming traffic exceeds the available queue capacity, some packets may be dropped.

**Advantages:**

* Helps regulate the output rate.
* Reduces sudden variations in the outgoing traffic rate.
* Provides a useful model for controlling bursty traffic.

**Limitations:**

* Traffic may be dropped when the queue is full.
* A fixed processing rate may not immediately accommodate sudden increases in traffic.

## 9. Experimental Results

The following measurements were reported for the selected configuration.

| Performance Metric                    | Token Bucket | Leaky Bucket |
| ------------------------------------- | -----------: | -----------: |
| Total packets sent                    |           94 |           86 |
| Total packets dropped                 |            6 |           14 |
| Maximum queue size after transmission |           16 |           16 |

These results represent one simulation configuration and should not be treated as universal performance guarantees.

### Interpretation

**Token Bucket:**

The simulation reported 94 packets sent and 6 packets dropped. The initial token availability and token accumulation may have helped the algorithm accommodate bursts, depending on the implementation.

**Leaky Bucket:**

The simulation reported 86 packets sent and 14 packets dropped. This behavior is consistent with the possibility that burst arrivals exceeded the queue's available capacity or processing rate.

**Comparison:**

Under the tested conditions, the Token Bucket transmitted 8 more packets and dropped 8 fewer packets than the Leaky Bucket.

Both algorithms reported a maximum queue size after transmission of 16. This metric should not automatically be interpreted as the maximum instantaneous queue occupancy.

The results depend on the traffic pattern, configured rates, bucket and queue capacities, initial tokens, and implementation details.
